# Supplied PSE: build and benchmark audit

The uploaded source tree has been preserved byte for byte. A source manifest before execution covers 88 files. No `build.rs` exists in the supplied workspace; the lockfile resolves registry dependencies, whose build steps are ordinary Cargo dependencies. A task-local Rust 1.95.0 toolchain was installed from the official rust-lang distribution, matching the version stated in the supplied Windows benchmark. The installer SHA-256 was checked against its official companion checksum. Exact installation and execution commands, compiler output and separate stdout/stderr logs are retained here. Initial local environment had no Rust installation or Cargo cache. Compilation uses a separate target directory outside the source tree. Execution status is in `executed_commands.json`; absence of a successful command record is not evidence of a passed test.

## What the harness measures

The supplied `benches/engine.rs` constructs deterministic synthetic JSON observations outside each timed pass. Parsing, digest verification, graph updates and (except in ingestion-only mode) macro-step work are inside the pass. The allocator wrapper remains installed even with counters disabled. Allocations are counted in a separate processing pass, not used as net heap/RSS. Five repetitions create fresh engine state, in a fixed workload order. Commit benchmarking relaxes gate and consensus thresholds and checks an initial nonempty commit workload. The main commit workload is 8 sources and 16 ticks; its per-run p95 and p99 are the maximum of only 16 tick observations, not a production tail estimate.

The Windows-only CPU and process RSS implementation is replaced by literal zero counters on Linux. Linux zeros are unavailable metrics, not zero resource use. Throughput is per input observation, whereas latency is per batch/tick. Engine construction and input generation are excluded. The scaling experiment runs independent states, not parallel workers sharing one state, and includes spawning, joining and final-state hashing. It has only one run per thread count. Current throughput does not include Gabriel canonical state copies, durable SQLite commits, semantic audit replay, a broker, network transport or replication.

## Workload boundaries affecting interpretation

The JSON `value` field is present and hashed/stored but does not supply a learned forecasting target or numeric graph feature in the benchmark adapter. Distinct sources, timestamps and phase hints are explicit. Graph edges reflect co-batch membership. Up to 64 unique batch source IDs, all pairs are linked; above 64 a two-neighbour ring is used instead. Thus the 65-source case is not a larger version of the same dense workload as 32 sources. Sources recur regularly with synchronized phases, favouring the existing converged-region optimization. The inherited performance document already restricts its large historical gains to such workloads.

The upload includes prior Windows outputs for original, extracted and optimized stages. Their historical source trees and executables are explicitly outside the delivery (`_pse_forensics/`) and were not inspected or rerun. Accordingly those old/new ratios are supplied measurements, not results reproduced in this environment. Frozen original fixture compatibility can be tested, but it is not a reconstruction of the unavailable original implementation.

## Reproducibility limits

`rust-toolchain.toml` tracks `stable`, despite a comment claiming to pin the toolchain; the same stale comment mentions MSRV 1.82, while Cargo.toml requires 1.89. This run explicitly selects Rust 1.95.0. A lockfile fixes dependency versions; it does not itself pin compiler, CPU, floating point behaviour or platform. Test results and benchmark values must be reported for the actual Linux/compiler environment recorded here. No claim of superiority to Kafka, Aladdin or Gabriel follows from the standalone PSE harness.
