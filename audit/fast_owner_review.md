# Independent review of the structural-copy owner

The reviewed implementation is `gabriel_runtime/fast_owner.py`; the executable independent check is `reproduction/check_fast_owner.py`. The recorded execution and source hashes are in `results/fast_owner_checks.json`, and its synthetic fixtures are in `results/fast_owner_inputs.json`. The original owner, canonical format and numerical adapters were not edited by this review.

## Result and scope

No implementation defect was found in the checked operational contract. The structural copy preserves exact permitted scalar values and types, list order, sorted dictionary iteration order, and separation of mutable containers. Repeated mutable aliases are expanded, as in the reference JSON round trip. Validated stored canonical state text is reused only after strict parsing and canonical-byte checking; the implementation does not retain a state cache across owner calls. SQLite admission, command identity, transaction boundaries, audit reconstruction and synchronization remain inherited from or equivalent to the reference owner.

The preservation argument requires deterministic adapters whose behavior depends on data values and container order. This is a substantive premise, not a statement about arbitrary Python code. An executed counterexample creates two fields containing one shared immutable string and asks whether their Python objects are identical with `is`. The reference binding returns `false`, while the structural-copy binding returns `true`. Both strings have identical values. The counterexample is intentionally outside the supported reducer contract and demonstrates why immutable object identity and allocation behavior are excluded. The manuscript's two preservation propositions make this scope explicit.

The comparison also assumes normal execution without allocation failure, interpreter corruption or asynchronous mutation by caller/adapter code during a call. These operational faults are not modeled by the source-level preservation argument. Python execution is not sandboxed. Adversarial test reducers exercise ownership and rejection; they do not establish isolation from malicious executable code.

## Executed verification

The final report contains exact counts and source bindings. Principal checks are:

- 261 accepted clone cases, including all 128 ASCII code points, maximum integer magnitude, depth 64, and 250 seeded recursively generated JSON objects. Contents, nested dictionary order and every mutable container's separation were checked against the reference decoder/encoder. Eighteen invalid cases exercise depth 65, cycles, non-ASCII data, exact-type subclasses, non-string keys, floats/nonfinite values and integer bounds.
- Five full profile paths: the legacy registry, and each of the original and incremental raw-stream registries at horizons 1 and 5. Each stream path uses 324 original synthetic records, six corrections, and one appended record, followed by retry, view, full semantic audit and cross-owner reopening. Every command receipt and every SQL field in all three tables are compared directly. Comparisons use canonical strings or the stored SQL values, not only digests.
- Deliberately mutating trusted test reducers modify input state, configuration, payload and view arguments. Later mutation of retained objects and returned receipts cannot change committed SQL data. Seven invalid reducer cases reject atomically in both owners, including exceptions after mutation, invalid state/result types, a cyclic result, malformed return pair and an overdeep enclosing record.
- The existing runtime core, budget, finite-observation, maturity, arithmetic-boundary, contract-isolation and corruption checks were rerun with `FastStore` in temporary stores. Their original result files were not overwritten. This includes command identity collisions, stale heads, timestamps, exact byte budgets, unchanged issued forecasts, rehashed semantic forgery, and external-head detection of a valid truncated prefix.
- Two owner implementations alternately access one database. Separate concurrent connections actually race on one expected head; exactly one succeeds and the other receives a stale-frontier rejection. Both implementations see the same final committed state.
- Live SQL state with duplicate keys, noncanonical whitespace or a forbidden floating-point value is rejected by both owners before transition or view. Rejected submissions leave all SQL rows unchanged.
- Two child processes terminate with `os._exit` immediately before or after the optimized owner's commit. Reopening through the original owner verifies rollback before commit and persistence after commit. Retrying causes exactly one effect and returns the stored receipt. This is process-failure recovery, not physical power-loss testing.

The tests do not establish new numerical accuracy, production throughput, cryptographic authenticity, hardware power-loss durability or a universal property over all Python adapters. Performance is measured separately under the benchmark's declared workload and environment. Full retained-state materialization and full semantic replay still have history-dependent costs.
